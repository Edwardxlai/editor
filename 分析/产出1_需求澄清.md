# 产出 1：需求澄清与问题定义

> PDF：「重点不是写一份长需求文档，而是展示你如何把一句模糊需求转化为可执行任务。」
> 所以本文只有两部分：**问题定义**（一段）+ **待确认假设**（按人/流/钱量/暗/界五类）。
> 每条假设必须带「不成立会怎样」——PDF 要求「说明你的假设**及其影响**」，只列问题不写影响等于没澄清。

---

## 一、问题定义

负责人的原话是「我不要一个把录音转成文章的工具」。

我把它改写成：

> **编辑的瓶颈不是把 3 小时录音变成文章，是判断不可复用。**
>
> 同一段素材，不同编辑对"什么值得写、哪句需核实、哪条历史笔记能引"的结论不一致；且这些判断只发生在编辑脑中，写完即散，下一篇换个人从零再来。题目自己列的第二条痛点说的就是这件事，"处理成本高"只是它的结果。
>
> 因此本工具的目标不是产出文章，而是**把编辑的判断固化成可检查、可追溯的中间产物**（观点—证据主表、角度备选、待核清单、复用建议），让编辑在这些产物上做最后一层判断，而不是在原始逐字稿上从头判一遍。

**可验证的成功条件**（须与业务方共同确认，见 §钱量）：

1. 编辑从"拿到逐字稿"到"产出可发初稿"的耗时下降，且下降不是转移到核实环节
2. 同一素材由不同编辑处理，产出的要点集合重合度上升
3. 已发布文章中的事实性表述，可回溯到逐字稿说话人与时间戳的比例上升

## 一点五、如果只能问三个问题

29 条不可能一次问完，也不该一次问完。**下面这三条是"不问就不能动工"的，其余都可以先按默认值跑起来再校准。**

| 顺位 | 问题 | 编号 | 为什么是它 |
|---|---|---|---|
| 1 | **素材版权归属：录音、逐字稿、历史笔记分别属于谁，可否作为模型输入？** | 25、22 | 答案是"不可以"的话，整个方案换地基——本地模型、段表容量从百篇降到十篇、"不上 RAG"的结论要推翻。这是唯一一条**答错就全盘作废**的 |
| 2 | **现在一篇的真实投入：多少人、多少工时、返工几轮？** | 11 | 没有基线，"提效"这个词就没有对象。做完也无法证明有用，验收时会变成各说各话 |
| 3 | **编辑真的是对着逐字稿一句句写吗？还是先听录音记要点、逐字稿只用来查证？** | 5 | 决定主交付物是谁。若逐字稿只是查证工具，`evidence.md` 才是产品，`draft` 降为附赠——六个文件的主次颠倒 |

**为什么不是别的**：13（质量怎么衡量）和 28（出错谁负责）同样要命，但它们可以在试点之后再定；上面三条必须在写第一行代码之前定。

## 二、待确认假设

### 人 —— 谁用、给谁看

| # | 要确认的 | 不成立会怎样 |
|---|---|---|
| 1 | **使用者是执笔编辑，还是审核/主编？** | 执笔者用 → 中间产物要全（outline 承载全部要点）；审核者用 → 要的是差异对照与风险清单，六个文件的主次完全颠倒 |
| 2 | 协作编辑（多人）如何分工，是否需要同一份中间产物多人共用 | 需要 → 输出得能合并、能标注谁改了哪条，本版单机跑一次的形态不够 |
| 3 | `content_brief.md` 的目标读者是每篇一变，还是账号级固定 | 每篇一变 → 角度筛选必须以 brief 为输入；账号固定 → 可预置 |
| 4 | 历史笔记的 `适用读者` 字段由谁填、按什么口径 | 口径不一 → 该字段不可用于自动排除（实测 8 篇中 7 篇与本次 brief 有交集，本就零区分度） |

### 流 —— 现在到底怎么干

| # | 要确认的 | 不成立会怎样 |
|---|---|---|
| 5 | **编辑真的是对着逐字稿一句句写吗？** 还是先听录音、边听边记要点，逐字稿只用来查证？ | 若逐字稿只是查证工具 → 本工具的定位从"替代通读"变成"替代查证"，evidence.md 反而是主交付，draft 是附赠 |
| 6 | **逐字稿怎么来的**——ASR 自动转写、外包听录，还是编辑自己整理？ | ASR → 错字和说话人错标是常态，`editorial_checks` 的「缺失信息」一节是刚需；人工听录 → 这类风险低，该模块可弱化 |
| 7 | 逐字稿有没有前置的清洗/断句/说话人校正环节 | 没有 → 本工具要承担片头识别、口播识别、说话人存疑标记（本版已做） |
| 8 | **反复做的固定动作有哪些**——找金句？核数字？查历史稿？配案例？ | 这决定六个输出里哪个最该做深。目前是按题目 bullet 平均用力，没有依据 |
| 9 | 编辑 SLA 是多久，急稿和常规稿流程一样吗 | 有急稿档 → 需要一个"只跑 evidence + checks"的快模式 |
| 10 | 一场访谈是产一篇还是拆多篇（短内容/视频选题） | 拆多篇 → `angles.md` 的 3 个角度不是备选而是**并行选题**，不该收敛到 1 个 |

### 钱量 —— 花多少、怎么算成功

| # | 要确认的 | 不成立会怎样 |
|---|---|---|
| 11 | **现在一篇的真实投入**：多少人、多少工时、返工几轮 | 没有基线就无法证明提效。这是产出 1 里最该先拿到的数字 |
| 12 | **主要返工点在哪**——观点选错、结构推翻、事实被打回，还是文风不对 | 返工集中在文风 → 本方案（重判断轻成文）方向就错了 |
| 13 | 「内容质量提升」用什么衡量：阅读量？编辑主观评分？事实差错率？ | 用阅读量 → 与本方案冲突（本方案明确禁止用无证据的抓眼球表述做标题） |
| 14 | 「编辑效率提升」是否允许把时间转移到核实环节 | 不允许 → 待核清单必须同时给出核实建议，而不只是列出风险 |
| 15 | 模型调用成本上限；单篇可接受的 API 花费 | 上限很低 → 现方案一次抽取已是最省形态，无进一步压缩空间 |
| 16 | 这个产品不起作用的损失是什么——只是维持现状，还是已有排期依赖它 | 有排期依赖 → 必须先交可用的最小路径而非完整六件套 |

### 暗 —— 没写在流程图上的真实情况

| # | 要确认的 | 不成立会怎样 |
|---|---|---|

| 18 | 历史笔记复用现在真的发生吗，还是"理论上应该复用" | 实际很少发生 → 复用模块优先级下调，不该占方案篇幅 |
| 19 | 素材里的口播/广告段（本次字幕 29–30、53 前半）现有流程怎么处理 | 有既定处理惯例 → 直接沿用，不必我另立判据 |

### 界 —— 不能碰的线、出事谁负责

| # | 要确认的 | 不成立会怎样 |
|---|---|---|

## 三、本版实现所采用的假设

以下按"成立"实现，均在代码或交付物中标注，业务方推翻任一条即触发对应改动：

| 假设 | 影响面 |
|---|---|
| 逐字稿可发送第三方 API | 全流程 |
| 500–800 字非硬卡，「合理即可」（已确认） | `draft_v0_5.md` |
| 时效**不设硬阈值**：按篇级日期＋主题由模型判，只影响"能否作事实依据"，不影响能否作历史参照 | 历史笔记可用性判定 |
| 同源笔记应拦截而非提示 | `reuse_suggestions.md` |
| 3 篇样稿只能支撑暂定 style card | 风格与标题型 |
| 未来输入量在百篇内 | 不上 RAG / embedding / 向量库 |
| 历史笔记段表存编辑定稿后内容，非 AI 初稿 | 段表接入时点 |
| 脱敏以 README 声明为准，遗漏项交编辑决定 | `editorial_checks.md` |

> 全部阈值均为 MVP 默认值，**无业务校准依据**，不得作为业务真理使用。
