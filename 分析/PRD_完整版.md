## 1. 产出 1：需求澄清与问题定义

### 1.1 我看到的核心矛盾

编辑的时间花在**重建上下文**上，价值却只产生在**做判断**上。

一场 90 分钟访谈进来，编辑要先通读、记住谁在什么时候说了什么、翻回去找原话、判断哪句数据没出处、回忆历史笔记里有没有相关案例——这些是机械劳动。真正值钱的是之后那四个动作：**选角度、核事实、定结构、定表达**。

而 AI 在内容生产里的常见用法，恰好把这两件事的位置搞反了：

| | 谁来做 | 应该谁来做 |
|---|---|---|
| 挑重点、下结论、定调子 | AI（摘要/生成） | **编辑** |
| 找原话、对时间戳、标待核项、翻历史库 | 编辑 | **AI** |

"把逐字稿转成文章"之所以不成立，不是因为写得不好，是因为它做的是上面那一格。负责人那句"最后一层判断仍然由编辑完成"，说的就是要把这张表翻回来。

### 1.2 诉求改写：可交付、可验证的产品问题

> **原始诉求**：我不要一个把录音转成文章的工具。我需要 AI 帮编辑更快找到真正值得写的观点，保留证据，形成可编辑的内容初稿；最后一层判断，仍然由编辑完成。

改写为：

> **输入**一场访谈的逐字稿（带说话人与时间戳）＋ 历史笔记库，**输出**一套**证据锚定的编辑工作包**——6 份结构化 Markdown 文件，其中每一条判断都能回指到具体的字幕序号、时间戳和说话人；每一条无出处的事实性说法都已被标出；每一条历史素材的复用与否都附判断理由。
>
> 使编辑跳过"通读 → 摘要 → 找证据 → 翻历史"这段重建上下文的劳动，直接进入选角度、核事实、定结构、定表达四个判断动作。

**这个问题是否被解决，可以这样验证**：

| 验证项 | 判据 | 可自动化 |
|---|---|---|
| 可运行 | 一条命令跑通，产出 6 个文件 | ✅ |
| 可溯源 | 抽查 evidence 中任意条目，原话能在 SRT 中字面命中 | ✅ |
| 有判断 | outline 的两级标题都是判断句而非名词短语 | 人工 |
| 可编辑 | 编辑在 draft 上的动作以"加"为主而非"删"（见 §1.5 反指标） | 人工 |
| 边界清楚 | 无出处的说法不出现在标题位和结论位 | 半自动 |

**明确不是什么**（避免跑偏）：

- 不是产出一篇接近成品的文章。版本号是 **v0.5**，不是 v1。
- 不是全自动流水线。所有输出默认为草稿，无一可直接发布（见假设 A5）。
- 不是通用内容生成器。它服务于"访谈 → 商业笔记"这一条链路。

### 1.4 需求边界：本版不做什么

| 不做 | 理由 |
|---|---|
| Web / H5 界面 | 题目允许命令行脚本；界面不构成评审锚点（"是否输出可编辑、可溯源、有判断的内容结果"） |
| 多篇访谈批处理 | 单篇跑通即验证核心判断 |
| 编辑反馈回流训练 | 无数据、无标注、无基线 |
| 自动发布 | 与"最后一层判断由编辑完成"直接冲突 |
| 分读者群的内容变体 | 依据不足，见 C4 |

### 1.5 成功指标（代理指标，需业务方校准）

因为质量无法直接测量，这里全部使用**可观测的代理指标**，并显式标注它们代理的是什么。

**效率侧**

| 指标 | 定义 | 基线 |
|---|---|---|
| 素材到 v1 时长 | 编辑收到工具输出 → 提交可发布初稿 | 现状 2–3 天（待 D3 确认） |
| 溯源查找次数 | 编辑为找一句话的出处而回翻逐字稿的次数 | 目标趋近 0（证据已内联） |

**质量侧**

| 指标 | 定义 | 可自动 |
|---|---|---|
| 证据覆盖率 | draft 中的核心判断带内联证据标记的比例 | ✅ 目标 100% |
| 溯源准确率 | 抽样条目的原话能在 SRT 中字面命中的比例 | ✅ 目标 100% |
| 待核项召回 | 含数字/机构/岗位影响的说法进入待核清单的比例 | 半自动，目标 100% |
| 要点保留率 | 编辑最终成稿中，来自 `outline.md` 的要点占比 | 人工 |

**反指标（这几个才是真正判断"有没有写满"的）**

| 反指标 | 含义 | 阈值 |
|---|---|---|
| **删除率 > 增加率** | 编辑在 draft 上删的字多于加的字 → 说明 AI 写满了，方向错误 | 删除率应 < 增加率 |
| 待核项漏报 | 编辑发现了工具没标出的无出处说法 | 应为 0，出现即为严重缺陷 |
| 错误溯源 | 证据标记指向的位置说的不是那句话 | 应为 0，出现即丧失可信度 |

> 反指标之所以重要：一个把逐字稿扩写成 8000 字的工具，在"效率"和"覆盖率"上都会得高分，但在删除率上会暴露——编辑的时间被转移到删除废话上，总耗时可能不降反升。

## 2. 产出 2：方案设计

### 2.1 全流程总览

```
【离线，一次性】
  Stage 0a  历史笔记入库 ─────→ segments.jsonl（关键段表）
                              └→ notes_meta.jsonl（篇级元数据）
  Stage 0b  样稿风格归纳 ─────→ style_card.md

【单次运行】
  data/interview_transcript.srt
        │
        ├─ Stage 1  解析（纯代码）──────→ 字幕单元表 cues[97]
        │
        ├─ Stage 2  观点抽取（LLM×1）──→ evidence 主表 ★
        │                                  │
        │     ┌────────────────────────────┤
        │     │                            │
   Stage 3    Stage 4                  Stage 5
   历史复用    角度生成                 结构与初稿
   (LLM×1)    (LLM×1)                  (LLM×2)
        │          │                       │
        └──────────┴───────────────────────┘
                       │
                 Stage 6  渲染（纯代码）
                       ↓
   outputs/  angles.md  outline.md  evidence.md
             reuse_suggestions.md  draft_v0_5.md  editorial_checks.md
```

**★ 主表原则**：抽取只跑一次，产出一张 evidence 主表。其余五个文件**不重复抽取**，只做筛选、排序与引用。

| 文件 | 与主表的关系 |
|---|---|
| `evidence.md` | 主表本身 |
| `editorial_checks.md` | 筛 `type=事实` 且无出处的行 ＋ 转录风险项 |
| `outline.md` | 挑要点、组结构，引 `P` 编号 |
| `angles.md` | 从主表选落点，引 `P` 编号 |
| `draft_v0_5.md` | 正文内联 `[P08 字幕33]`，时间戳与说话人由代码补全 |
| `reuse_suggestions.md` | 段表 × 主表的匹配结果 |

这样设计的直接收益：**证据溯源天然成立**。角度引 P 编号，P 编号本来就挂着说话人和时间戳，不需要额外维护一套映射。

### 2.1.1 贯穿全流程的原则：能用代码算出来的事实，不问模型

模型只负责一件它不可替代的事：**从原文里挑出哪句话值得引**。

说话人是谁、时间戳是多少、这句话在第几条字幕、字符偏移量是多少 ——
**全部由代码从原文反查得出**，模型给的值一律被覆盖。

| 项 | 谁提供 | 为什么 |
|---|---|---|
| 引哪句话 | 模型 | 需要判断，代码做不了 |
| 这句话在第几条字幕 | **代码**（按原话反查） | 可算，且模型算错无法被发现 |
| 时间戳、说话人 | **代码**（从字幕表取） | 同上 |
| 历史笔记的字符 offset | **代码**（`find_offset`） | 模型给的偏移量无法校验 |
| 这句话是否真的存在于原文 | **代码**（`locate_quote`） | 这是"可溯源"承诺的唯一验证点 |

这条原则带来两个结果：

1. **溯源信息正确不是靠模型自觉，而是结构上不可能错。**
2. 模型唯一还可能犯的错 —— 引了原文里不存在的话（改写、杜撰）——
   会被 `locate_quote` 当场抓住，整批打回或丢弃。**错误面被压缩到一个可测的点上。**

⚠️ 反过来说，这条原则也划出了本方案的能力边界：它保证"这句话确实是他说的"，
**不保证"他说的是对的"**。后者是编辑的工作，见 §2.4。

### 2.2 逐 Stage 规格（输入 / 输出 / AI 介入方式 / 为什么）

#### Stage 0a：历史笔记入库（离线，一次性）

| | |
|---|---|
| **输入** | `historical_notes.jsonl`（8 篇，正文合计 372,942 字【实测】） |
| **输出** | `segments.jsonl`（关键段表）＋ `notes_meta.jsonl`（篇级元数据） |
| **AI 介入** | Prompt，**一篇一次调用**。8 篇 = 8 次 |
| **触发** | 手动，`python ingest.py`。历史笔记是静态的，抽一次永久复用 |

**一篇一次，能不切就不切。**

单篇上限 **100k token**（目标模型上下文约 200k，取一半留足输出与思考链余量）。
按保守估计 1.5 字/token 换算为 150,000 字。实测最长的 note_05 是 82,978 字 ≈ 5.5 万 token，
**8 篇全部一次进得下**。

> ⚠️ 早期版本按 24,000 字硬切，8 篇切成 20 次调用。这是个错误，有两处代价：
>
> 1. **取舍质量**：段上限被按块摊薄（`12 ÷ 4 块 = 3 段`），模型变成"在这 1/4 篇里挑 3 段"，
>    它看不到全篇就做不了取舍 —— 这和 §2.2 Stage 2 逐字稿不分段是同一个道理，
>    当时没在历史笔记这边贯彻。
> 2. **成本**：贪心切法在末尾留下极小的尾巴块。实测 note_04 的尾巴块只有 1,117 token 输入，
>    照样烧掉 8,335 token 输出（成本主要在思考链上，与输入长度无关）。
>    20 次里有 3 次是这样白花的。
>
> 现已改为：token 阈值 + 均衡分块（`chunk_by_sentence` 按"总长 ÷ 块数"填而非贪心填满）。
> 分块成为**只在超限时才走的降级路径**，走到时会显式告警说明取舍质量会下降。

**段表 schema**（段上只挂 `note_id`，不冗余元数据）：

```jsonc
{
  "seg_id":   "note_03#04",
  "note_id":  "note_03",
  "offset":   [3120, 3580],          // 指回原文字符区间，可校验
  "claim":    "中间层能力正在被侵蚀，价值向两端集中",   // 判断句，匹配用的就是它
  "quote":    "……",                  // 整句边界的原文，给编辑看
  "topic_tag":"幂律分布/中间层侵蚀"
}
```

**元数据 schema**（每篇一条，独立存放）：

```jsonc
{"note_id":"note_03","标题":"…","日期":"2026-06-05",
 "主题":"…","适用读者":"…","可引用范围":"…"}
```

**为什么元数据不冗余到段上**：元数据会变（业务方可能随时收紧某篇的 `可引用范围`），冗余就得全表更新。而且两层判断天然属于不同粒度：

- **篇级** → 合规约束（时效 / 可引用范围 / 适用读者），作用在 `note_id`
- **段级** → 内容匹配，作用在 `seg_id`

匹配到某段后拿 `note_id` 查回篇级约束，就能得出"这段内容对得上，但按 `可引用范围` 只能当框架不能引结论"这种结论。

**为什么段表存判断句而非原文片段**：更短、噪音少，对匹配更有利；且与 Stage 5 产出的 outline 形态一致，可以直接增量接入（见 §2.6）。

**这里是全流程唯一需要切块的环节**，且必须按标点切出的**整句**，不允许模型自由划字符区间——自由边界的标注一致性极低（同类任务的公开数据集实测 Krippendorff α < 0.2 以致数据作废），句子级边界才可复现。

#### Stage 2：观点抽取（LLM × 1）★ 核心

| | |
|---|---|
| **输入** | 字幕单元表**全文**（12,677 字，97 条，49.1 分钟）【实测】＋ `content_brief.md` |
| **输出** | evidence 主表（JSON） |
| **AI 介入** | Prompt，**单次调用，全文一次进，不分段** |

**为什么不分段**：逐字稿只有 1.2 万字，任何模型一次读得下，分段没有收益，且会**切断跨段关系**。实例：字幕 36 的限定语（"这里我说的不是某个确定行业马上会发生什么"）限定的是字幕 38 的数据（终生收入下降超五分之一、第一年死亡率翻倍）——划段极可能把两者分开，第二次调用就再也看不见它们的关系。

**evidence 主表 schema**（以本次实跑的 P01 为例，`outputs/_intermediate/evidence.json` 可对照）：

```jsonc
{
  "point_id": "P01",
  "title": "AI使用者与不使用者的差距正在扩大",   // 判断句，不是名词短语
  "type": "观点",                            // 观点 | 案例 | 因果链 | 事实
  "claim": {                                 // 观点原话：他主张了什么
    "quote": "这是一个正在扩大和加剧的差距。如果有人在使用AI，他们就能完成多得多的任务，并且感受到前所未有的能动性。",
    "speaker": "嘉宾B", "cue": 11, "ts": "00:02:09"
  },
  "qualifier": {                             // 限定语，可为 null
    "quote": "这里我说的不是某个确定行业马上会发生什么，而是提醒大家，不适应工具的人会承受更高风险。",
    "speaker": "嘉宾B", "cue": 36, "ts": "00:12:49"
  },
  "support": [                               // 他为什么这么认为：理由 / 推导 / 举例，一行一条
    {"quote":"如果他们仍然对此感到紧张，或者还没接受过培训，你就会看到这种差距在拉大。",
     "speaker":"嘉宾B","cue":11,"ts":"00:02:09"}
  ],
  "verification": "无需核实",                // 无需核实 | 需核实 | 无出处
  "flags": [],                               // 片头 | 口播特征 | 说话人存疑 | 术语不统一 | 无出处事实
  "why": "全篇“能动性差距”论的落点，也是核心主张：差距不是注定的，取决于是否使用和培训。"
}
```

> `why` 字段渲染成 `evidence.md` 里的「为什么值得写」一行。它是给编辑的取舍理由，
> **不参与任何自动校验**——它不是原文引用，所以不受 `locate_quote` 约束，也不该被当作证据读。

**五条硬规则**：

**① 观点原话与印证原话必须分开记，印证一行一条。**
时间戳和说话人是跟着**印证**走的。塞进同一个单元格，`draft_v0_5.md` 就没法在具体句子上挂精确标记。

**② 支撑为空必须显式写"无"，不得省略；但空栏对两类要点意味着不同的事。**

**空栏本身就是信号**——省略掉它，等于把"没有证据"和"没抽到证据"混为一谈。但这个信号要读对，得先分清这一栏在问什么：

| 类型 | `support` 装的是 | 空着意味着 |
|---|---|---|
| `事实`（含数字、研究、机构、比例） | 他拿什么**证据**支持这个数字 | 🔴 红灯：全篇无出处，写进正文前必须核 |
| `观点` / `案例` / `因果链` | 他**为什么这么认为**（理由、推导、举例） | 正常：他直接下了判断没展开，不是缺陷 |

**早期版本对两者一律打「纯断言」标记，是范畴错误。** 它让「同等教育成本降到约 100 美元」（无出处的事实）和「企业家就是能动性的同义词」（定义式判断，本来就不需要外部背书）长得一模一样——而区分这两件事恰恰是本工具最该做的。

对照实例：P08「智能成本归零的说法不负责任」是观点，它的 support 装的是「除了语言智能，还有感知、空间、身体、情感智能」——那不是"证据"，那是"他为什么这么想"，正是编辑扩写时要用的东西。

**③ 类型标签用题目自己的词：观点 / 案例 / 因果链 / 事实。**
不自造分类体系，也不引外部论文的。题目已经列好了：

> 产出 2：如何识别和保留关键**观点**、**案例**、**因果链**与原始**证据**
> 产出 3：需要编辑人工确认的**事实**、风险或缺失信息
> brief：**数据、外部机构、公司案例、岗位影响**等事实性说法，需要标注**核实状态**

打标签的唯一目的是**分流到不同输出文件**。不在抽取时标，下游每个文件都得重判一次。

**④ 限定语挂成字段，不作为独立条目。**
限定语本身不是判断，是对别的判断的约束，单独抽出来下游无法使用。挂成被限定条目的字段，并立硬规则：**带限定语的条目，引用主张时必须同时带上限定语。**

丢掉限定语再引用主张，就会把话写满——正是题目点名的失败模式。

【实测】与同源笔记逐句 diff 后确认，以下三句**只存在于 SRT**，且全部是限定语：

| 字幕 | 说话人 | 内容 |
|---|---|---|
| 6 | 主持人 | 未来三年大量白领岗位会被 AI 替代……**但我还没有看到明确证据** |
| 26 | 嘉宾A | 也确实看到一些重复性任务正在被工具接管，**所以这里既不能夸大，也不能假装没有变化** |
| 36 | 嘉宾B | **这里我说的不是某个确定行业马上会发生什么，而是提醒大家，不适应工具的人会承受更高风险** |

**⑤ 片头剪辑不作为证据。**

播客片头会把后面的精彩片段剪到开头做钩子。本篇片头是字幕 1–7（00:00:00–00:01:07），字幕 8 主持人问"您现在经营着好几家公司，您看到了什么？"才是正片开始。

实测对应关系：字幕 2 ← 57（27:42）、字幕 1 ← 31（08:58）、字幕 4 ← 11（02:09）、字幕 5/7 ← 39（14:29）。

**规则：证据一律指向正片对应位置。** 做法是写进抽取 prompt，**不写检测算法**——片头在结构上一眼可见（开头几条互不衔接、没有问答流），模型一次读完全文自己认得出。为模型顺手能做的事写集合运算，属于自找麻烦。

> 顺带一个值得在成稿里讲的点：字幕 6 那句"未来三年大量白领岗位会被 AI 替代"**就在片头里**——最抓眼球的话本来就是为效果剪进预告的，而说话人自己在同一句里声明了"我还没有看到明确证据"。这正是 brief 说的"抓眼球但缺少事实支撑的表达，不应直接做标题或定论"。

#### Stage 3：历史素材复用判断（LLM × 1）

| | |
|---|---|
| **输入** | 关键段表（全部 8 篇）＋ 字幕单元表全文 ＋ 篇级元数据 |
| **输出** | 复用建议（含同源判定） |
| **AI 介入** | Prompt，单次调用 |

**匹配方向：用历史的关键段去找输入文章，不是反过来。** 小对小，比拿特征词扫 37 万字既准又省。

**不做 RAG、不做 chunking（除 Stage 0a 入库）、不做 embedding、不做 BM25**——理由见 §2.3。

**同源识别由代码算，在发 prompt 之前就完成，不问模型**（§2.1.1 原则的直接应用，完整口径见 §2.6）。

【实测】`historical_notes.jsonl` 第 2 条（《关于AI、能动性与未来的对话》，2026-07-27）是本次访谈的另一版整理稿，97 行逐条对应。运行时用的**覆盖率**口径下，note_02 = **0.8913**，其余七篇 ≤ **0.0001**，差三个数量级，阈值取 0.30 落在鸿沟正中间。

> 早期方案曾主张"交给 LLM 判，因为阈值只在一个样本上验证过、改写型同源可能漏过"。已推翻：
> 漏报风险两种做法都有，但代码这条至少**结果可复现、可离线回归**（`selftest.py` 已覆盖），
> 而让模型读两份长文本自己"感觉像不像同一场"既贵又不稳定，且错了没有任何抓手。
> 改写型同源属于已知残留风险，写在 §4-E4 假设里，不靠换成模型来掩盖。

**同源的真实风险不是"抄袭"，是循环佐证**：用素材本身佐证素材本身，并制造"已有历史观点支持"的错觉。此外两版脱敏口径不一致，存在未脱敏信息回流污染当前材料的风险（见假设 A5）。

#### Stage 4：角度生成（LLM × 1）

| | |
|---|---|
| **输入** | **evidence 主表** ＋ `content_brief.md` ＋ style_card 的标题句式 |
| **输出** | 3 个标题/切入角度备选【题目写死】 |
| **AI 介入** | Prompt |

**硬规则：生成角度时输入 evidence，不输入逐字稿原文。**

理由——把整篇原文丢给模型让它"提炼角度"，等于让它自己找重点。它做不到取舍，只能取平均，输出全篇的最大公约数，也就是那句正确的废话（"AI 不会取代你，会用 AI 的人会"）。**平庸是这个操作本身决定的，不是提示词写得不好。**

evidence 主表已经是做完取舍的结果：判断句、带说话人、带时间戳、带限定语字段、印证栏空的一眼可见。喂它进去，模型不用再找重点，只需要在给定落点上选和写。

> 这与实践经验一致：给 AI 一份**厚 brief** 生成的内容，质量明显高于把整篇文章塞进去让它自己读——厚 brief 的重点是人挑好的。区别在于这里的厚 brief 由 pipeline 自己产出，不用手写。

**推论**：抽取质量直接决定角度质量。evidence 抽漏的东西，角度阶段再也找不回来。所以 Stage 2 是全流程的质量瓶颈。

#### Stage 5：结构与初稿（LLM × 2）

| | 5a 结构 | 5b 初稿 |
|---|---|---|
| **输入** | evidence 主表全量 ＋ 选定角度 | 选定角度 ＋ `outline.md` ＋ evidence 主表 |
| **输出** | `outline.md` | `draft_v0_5.md` |
| **约束** | 两级标题树，每级都是判断句；每个二级标题挂 ≥1 个 P 编号 | 连贯成篇（不是提纲的展开）；核心判断内联 `[P08 字幕33]` |

**为什么拆成两次调用**：让 draft 基于已定稿的 outline 生成，保证两个文件不打架。一次调用同时产出结构和正文，模型会在写正文时偏离自己刚定的结构。

**为什么 outline 是标题树而不是要点清单**：【实测】三篇样稿的结构一律是 `一、` → `1.` → 要点的两级判断句树（`store/style_samples_raw.md`）。编辑照着它动笔，所以它要回答的是"文章怎么走"。原话不进 outline —— 那是 evidence 的活，抄一遍就变成第二张证据表。

**标题由程序透传，不让 5a/5b 的模型重写。**【实测】不透传时它会漂：angles 给出「开发一个应用的时间已缩到一个周末」，draft 交回「开发一个应用只需一个周末」。编辑选的是哪个角度，交付物就得是哪个角度，这是代码能保证的事。

**没进结构的 P 编号只用一行交代**。它是给编辑的指针，不是需要逐条读的清单；早期版本做成带理由的表格，形态过重。

【实测】本次 16 条要点中 12 条进结构，末行交代：`未进入本结构的要点：P09、P10、P11、P13 —— 见 evidence.md`。

> **这四条恰好就是全部四条「无出处」的事实类要点**（终生收入下降超五分之一 / 教育成本约 100 美元 / 用 AI 学习省 60% 时间 / 学校 10 年后不复存在）。
> 结构阶段自己把它们挡在了正文之外，与 R4「无出处的说法不出现在标题位与结论位」的方向一致。
>
> ⚠️ 但这是**本次运行的结果，不是机制保证** —— prompt 里没有"无出处不得进结构"这条硬约束，
> 代码也没有校验它。当作机制写进方案是不诚实的，所以只作为实测记录留在这里。若要成为保证，
> 需在 Stage 5a 加一条硬校验（未做，属已知缺口）。

#### Stage 6：渲染（纯代码，无 AI）

JSON → 6 个 Markdown。所有格式约束在代码侧校验（见 §3.7），不依赖模型自觉。

### 2.3 AI 介入方式：为什么不用 RAG / Agent

题目要求说明每一步的 AI 介入方式（Prompt / RAG / Agent / 工具调用）。本方案的答案是：**全部是 Prompt，共 5 次 LLM 调用（＋离线入库若干次）。没有 RAG，没有 Agent，没有工具调用。** 这是有意的取舍，理由如下。

| 技术 | 不用的理由 |
|---|---|
| **RAG / embedding / 向量库** | 检索是为了"从大量内容里找出相关的少量"。这里的两侧都不大：逐字稿 12.7k 字一次读得下；段表 8 篇约 8k 字也一次读得下。**没有需要被检索的规模**。上向量库只会引入召回损失（该匹配的没匹配上）和额外依赖，换不来任何东西 |
| **chunking** | 同上，且分块会切断跨段关系（字幕 36 限定字幕 38 就是活例） |
| **BM25 / 关键词召回** | 【实测】8 篇笔记的元数据里有 6 篇的特征词命中为 **0**（见 §5.1）。关键词方案在这份数据上直接失效 |
| **Agent 框架** | 流程是固定的 6 个 Stage，DAG 已知，没有需要模型自己决定下一步的地方。Agent 只会引入不确定性和调试成本 |
| **工具调用 / function calling** | 无外部工具需求。事实核实交给编辑（见 §2.4），不做联网核查 |

**规模边界说清楚**：单张段表能撑到**百篇量级**（预留 system prompt、输出和安全余量后的保守估计）。8 篇远未触顶。超过之后再分表或上检索层——**那是规模问题，不是这一版的问题。** 提前上 RAG 是拿确定的复杂度换不确定的未来收益。

**依赖清单**：一个 HTTP 客户端 ＋ `python-docx`。就这两个。

### 2.4 编辑做什么、AI 做什么

| 环节 | AI | 编辑 | 为什么这样分 |
|---|---|---|---|
| 通读、结构化、找原话、对时间戳 | ✅ 全做 | — | 机械劳动，AI 快且不会累 |
| 抽取候选要点、打类型标签 | ✅ 提候选 | 审 | AI 提全，编辑砍 —— 漏比多贵 |
| 判断哪条要点值得写 | 提排序建议 | ✅ **定** | 观点价值判断，负责人明确要保留给人 |
| 标出无出处的事实性说法 | ✅ 全做 | 审 | AI 擅长穷举，人擅长判断严重性 |
| **核实**这些说法真假 | ❌ 不做 | ✅ **做** | 无联网、无权威源；AI 核实等于编造置信度 |
| 历史素材匹配、查同源 | ✅ 全做 | 审 | 记忆型劳动，正是编辑现在漏案例的地方 |
| 判断历史素材**能不能用** | 提建议＋引限制原文 | ✅ **定** | 涉及合规与业务判断 |
| 搭结构、写初稿 | ✅ 出 v0.5 | ✅ **改到 v1** | AI 出骨架，人加理解 |
| 定标题 | 出 3 个备选 | ✅ **选/改** | 标题是立场表达 |
| 发布 | ❌ | ✅ | 见假设 D1 |

**一句话概括分工原则**：**AI 负责"这话在哪、有没有证据"，编辑负责"这话值不值得写、能不能这么说"。**

### 2.5 v0.5 的形态：一篇能读的文章，不是提纲的展开

【实测】已发布样稿实际 5,727 / 10,026 / 8,281 字，而题目原文要求 v0.5 是 500–800 字，差一个量级。

**字数已向出题方确认「合理即可」**，因此不再是门禁（口径见 §3.10）。**决策：只出 `draft_v0_5.md` 一份，不追加长版本** —— 字数既已放开，再拆一份 full 版就是重复。

放开长度之后，真正的约束落在**形态**上。最容易犯的错是把 outline 的每一节改写成一段话、四段并排交差 —— 那不是初稿，那是把结构文件抄了一遍，而编辑手里已经有一份了。

| ❌ 提纲的展开 | ✅ 初稿 |
|---|---|
| 每节一段，段与段之间没有关系 | 上一段的结尾把下一段的问题带出来 |
| 每段都从"嘉宾X说"开头 | 先立判断，原话用来钉住它 |
| 开头就是第一个小标题 | 有一个把读者拉进来的开场 |
| 写完最后一个要点就结束 | 落在一个判断上，留给编辑续写的接口 |

放开长度**不等于可以写满**：多写的每一句仍然得是判断或证据。"把嘉宾的口语表达写得过满、生成没有观点的正确废话"正是题目点名的失败模式。AI 给 8000 字大多是模型自填的过渡句，编辑要**删**；AI 给一篇结构完整的稿，编辑往上**加**。删比加累。

**三份文件的分工仍然成立**：`outline.md` 给结构、`evidence.md` 给全部证据原话、`draft_v0_5.md` 给可直接改的成文。编辑拿这三份扩写到样稿长度。

### 2.6 历史素材：如何用，以及如何不误用

题目原文只要求「**至少 1 条**历史内容的复用建议，或明确说明为什么不应复用」。四种情况各有写法：

编辑拿这份文件只想知道三件事：**哪一篇 / 用哪一段 / 放在新文章的哪一节。** 所以输出里**只报能用的**（`可用` / `有限复用`）。不相关的笔记不列 —— 编辑不会因为知道 note_05 讲的是组织管理而做出任何不同的决定。仅当一条都没匹配上时，才需要写清"查了什么、为什么都不适用"，因为那时候"找了但都不合适"和"没找"才是两件不同的事。

| 情况 | 输出内容 | 本次材料的实例 |
|---|---|---|
| **同源** | 在文件顶部一行报掉，不作为一条建议 | note_02（覆盖率 0.8913） |
| 匹配到但**受限** | 有限复用 ＋ **原文引用**该篇的 `可引用范围` 限制语 | note_01：「仅可作为历史背景或观点参照；不建议作为当前 AI 工具落地、模型能力或市场判断的事实依据」 |
| 匹配到且**可用** | 哪一段、放哪一节、怎么用、**禁止怎么用** | note_06 的默会知识内容 |
| 一条都没匹配到 | 查了什么、按什么标准、为什么都不适用 | 本次不适用 |

**同源判定由代码做，不问模型（§2.1.1 原则的直接应用）。**「这篇笔记有多少内容能在这份逐字稿里字面找到」是可计算量：

| | 字符 8-gram 覆盖率 |
|---|---|
| **note_02** | **0.8913** |
| 其余 7 篇 | 0.0000 ～ 0.0001 |

差三个数量级，任何阈值都分得开（取 0.30，落在鸿沟正中间）。让模型读两份长文本自己"感觉像不像同一场"既贵又不稳定，而这正是可以结构上保证的事。

> ⚠️ **note_02 在本项目里出现过三个数字，它们不是数据打架，是三次不同的计算。** 记在这里免得对不上：
>
> | 数值 | 怎么算的 | 出现在哪 |
> |---:|---|---|
> | **0.9252** | 数据勘察阶段的字符 8-gram **Jaccard**（note_02 全文 × 逐字稿） | §5.2，过程记录。**该算法未进入仓库代码** |
> | **0.9685** | `ngram_coverage(note_02 全文, 逐字稿)` | `selftest.py` 的离线回归断言 |
> | **0.8913** | `ngram_coverage(note_02 段表 quotes 拼接, 逐字稿)` | **`run.py` 运行时实际用的值**，进交付物 |
>
> **仓库代码里只有一个函数 `ngram_coverage`（有向覆盖率），没有 Jaccard。** 当初弃用 Jaccard 的原因写在
> `pipeline/textutil.py:180`：一篇 1 万字整理稿对 1.3 万字逐字稿，即使逐字对应，Jaccard 也只有 0.8 出头，
> 长度差会稀释交并比，而"这篇笔记有多少内容能在逐字稿里找到"本来就是有向的问题。
>
> **对外一律引用 0.8913**（交付物、README、讲解视频脚本都已统一）。§5.2 的 0.9252 保留原样，标注为勘察记录。

两处去重位置不同，问的也是两个不同的问题：

- **`ingest.py` 入库门禁**：库内互重 —— 同一篇内容的两个整理版本不能同时进库。库里躺着两份，任何一次复用判断都会重复命中同一批观点。【实测】本材料 8 篇互重最高 0.0010，本次无触发。
- **`run.py` reuse 阶段**：与本次输入同源 —— **不删库**（换一场访谈它就恢复可用），只在发 prompt 前过滤掉，且从候选池计数里扣除。

**剩下三道拦截交给模型，但相关性的门槛是硬校验的**：

| 拦截 | 判据 | 实例 |
|---|---|---|
| **不相关** | `matched_point` 必须落在 evidence 主表的 P 编号上，代码校验；填不出 P 编号即判不相关，整篇不进输出 | — |
| **过时** | 篇级日期 ＋ 主题时效性 | note_01 日期 **2023-07-09**，只能作历史参照，不能作事实依据 |
| **不适用** | 篇级 `可引用范围` / `适用读者` 与本次 brief 不符 | note_02 的范围写明"如用于企业管理者内容，需要说明适用对象差异"，而本次目标读者正是管理者 |

**为什么相关性要做成硬校验**：这是全流程最容易放水的一步。【实测】不设限时模型会为 7 篇里的 6 篇都找出一个理由；要求匹配必须落在要点表的 P 编号上之后降到 5 篇。要点表已经是"这场访谈里真正值得写的东西"，一段历史内容如果对不上任何一条要点，编辑不会为了用它专门加一节。

**关键设计：`可引用范围` 原文引用，不做机器解释。** 该字段是自然语言，把它编码成标签需要先定义标签体系，而现在没有依据支撑（见 §4-D）。工具的动作是把限制语**原样贴出来**并标"需编辑确认"，而不是替编辑判断"这算不算符合"。

### 2.8 异常处理矩阵

题目点名要求：数据不完整、转录有误、嘉宾表达含混、素材互相冲突时怎么办。

| 类别 | 具体情况 | 本次实例【实测】 | 处理动作 | 落点 |

### 3.4 六个输出文件的格式规范

#### `evidence.md`（主表）

```markdown
### P01 AI使用者与不使用者的差距正在扩大

- 类型：观点｜核实状态：无需核实
- **观点原话**：「这是一个正在扩大和加剧的差距。……」（嘉宾B 字幕11 00:02:09）
- **限定语**：「这里我说的不是某个确定行业马上会发生什么，……」（嘉宾B 字幕36 00:12:49）
  - ⚠️ 引用本条主张时必须同时带上该限定语。
- 为什么值得写：全篇"能动性差距"论的落点，也是核心主张：差距不是注定的，取决于是否使用和培训。

| # | 他为什么这么认为 | 说话人 | 字幕 | 时间戳 |
|---|---|---|---|---|
| 1 | 如果他们仍然对此感到紧张，或者还没接受过培训，你就会看到这种差距在拉大。 | 嘉宾B | 11 | 00:02:09 |
```

**支撑栏的表头随类型切换**，这是 §2.2 硬规则②「空栏对两类要点意味着不同的事」在渲染层的落地：

| 条目类型 | 表头 | 空着时 |
|---|---|---|
| `观点` / `案例` / `因果链` | **他为什么这么认为** | 正常 —— 他直接下了判断没展开 |
| `事实` | **有什么证据** | 🔴 无出处，进 `editorial_checks.md` 待核清单 |

两者空栏时渲染完全一样，靠表头把语义分开：

```markdown
| # | 有什么证据 | 说话人 | 字幕 | 时间戳 |
|---|---|---|---|---|
| — | **无** | — | — | — |
```

#### `angles.md`

3 个角度【题目写死】。每个包含：标题候选、切入逻辑、支撑的 P 编号、目标读者关联、**不能这么写的红线**（如涉及被限定或无出处的说法）。

#### `outline.md`

两级标题树（每级都是判断句）＋ 每个二级标题挂的 P 编号 ＋ 末尾一行列出未进入结构的编号。

#### `reuse_suggestions.md`

每条：`note_id` ＋ 篇级元数据摘要 ＋ 匹配到的段 ＋ **判断结论**（可用/有限复用/不复用）＋ 理由 ＋ 若有限制则**原文引用** `可引用范围` ＋ 建议放在哪一节 ＋ **禁止怎么用**。

#### `draft_v0_5.md`

连贯成篇的初稿，字数合理即可（§3.10）。核心判断内联 `[P08 字幕33]`，时间戳与说话人由代码补全。

#### `editorial_checks.md`

严格按题目三分法「需编辑人工确认的**事实、风险或缺失信息**」组织，章节号即题目的三个词：

| 章节 | 收什么 | 渲染位置 |
|---|---|---|
| **一、待核事实** | 说法原话 ＋ 位置 ＋ 核实状态（无出处 / 需核实）＋ 编辑要做什么 | `render.py:369` |
| **二、风险** | 2.1 说话人归属存疑　2.2 推广口播特征　2.3 脱敏口径不一致　2.4 同源历史素材 | `render.py:398` |
| **三、缺失信息** | 缺画面无法消歧的指代 ＋ 子节「术语不统一」「片头预告与正片的对应」 | `render.py:451` |
| 附：剔除与自动更正记录 | 工具丢了什么、为什么丢（**不做静默删除**）。本次无剔除，故未渲染 | `render.py:496`，条件渲染 |

**转录层噪音（时间戳重叠、超短片段）不进这个文件。** 判据是"编辑会不会因此改一个字"——不会。
它们由 `pipeline/srt.py` 照常检出并透传给抽取阶段（影响的是"这条能不能单独作证据"），
但不占编辑当天要读的篇幅。这条取舍与 README「`outputs/` 只放编辑当天要用的东西」是同一条原则。

⚠️ 早期版本把第三块叫「存疑信息（含题目所指的缺失信息，另收录转录疑误）」，
原因是转录错字既不是缺失也不是风险、无处安放。转录噪音移出后这个扩名就没必要了，**已改回题目原词「缺失信息」**。

⚠️ **脱敏遗漏**【实测】：材料声明已脱敏，但逐字稿正文里 **Claude、Gemini、Nano Banana、Twitter/X、TikTok、Substack 全是真名**，而 ChatGPT 被脱敏成「通用AI对话工具」、平台被脱敏成「某在线课程平台」。**口径不一致，不由工具替业务方决定，原样列出交编辑定**（对应假设 A5）。

实现：抽取 prompt 的第五类风险产出 `desensitization_gaps`（两类并列：原样出现的真实名称 / 已泛化的说法，各带字幕序号），渲染进 §3.2。**只做并列陈述，不建议统一口径，更不做反向识别**——README 使用边界明令禁止反向识别，所以 prompt 里写死了「不猜被泛化掉的是谁、不补网址、不写材料里没出现过的机构名」。

⚠️ 该项是 LLM 判定，**漏报无法被自动发现**（不像溯源有 `locate_quote` 兜底）。因此渲染时即使检出为空也会提示人工抽查，不写成「无」。

### 3.5 LLM 调用规格

| 调用 | Stage | 输入规模 | 输出 | 失败降级 |
|---|---|---|---|---|
| C0 | 0a 入库 | 整篇一次进（超 250k token 才切，≈150,000 字） | 段表 JSON | 见下；`quote` 在原文定位不到的段直接丢弃并记账 |
| C1 | 2 抽取 | ~13k 字 | evidence JSON | JSON 解析失败重试 1 次；再失败则中止并报错（不吞错） |
| C2 | 3 复用 | ~21k 字（段表＋逐字稿） | 复用判断 JSON | 同上；失败时 `reuse_suggestions.md` 写明"未完成匹配"，不伪造结论 |
| C3 | 4 角度 | evidence 主表 | 3 个角度 | 数量不足 3 则重试 |
| C4 | 5a 结构 | evidence 全量 | outline JSON | 校验"每节有 P 编号"，不通过则重试 |
| C5 | 5b 初稿 | outline ＋ 相关 evidence | draft | 字数只在**明显失控**时重试（见 §3.10）；小幅越界照常输出并在文件头标注偏离 |

**统一原则：宁可报错，不可伪造。** 任何一步失败都要在输出文件中显式说明，不能用兜底文本掩盖。这是"可溯源"的前提。

**三类失败必须分开处理**（前两类是实测踩到的，见 §3.9）：

| 失败类型 | 症状 | 处置 | 为什么 |
|---|---|---|---|
| **配置不足** | `finish_reason=length`，正文返回空 | **不重试**，直接抛错并给出修复指引 | 重试只会重复烧钱，改配置才有用 |
| **格式不合规** | JSON 结构损坏、字段缺失、类型非法 | 带着具体原因重试，仍失败则中止 | 模型有机会自己改对 |
| **溯源失败** | 某条引用在原文里定位不到 | 重试一次；仍失败则**只剔除该条并记账**，其余保留 | 见下 |

**第三类为什么不整批丢弃**：实测中出现过 13 条要点里 1 条的引用被模型悄悄删掉了插入语，
按"整批打回"处理会浪费 4 分钟和 3 万 token，而剩下 12 条完全合格。

但"保留"绝不等于放行 —— 剔除策略严格遵守两条：

1. **未经验证的引用一律不进入任何交付物。** 定位不到就是定位不到，不猜、不模糊匹配。
2. **不做静默删除。** 每一条被剔除的引用连同原因写进 `editorial_checks.md` §6.1，
   编辑必须能看见"工具丢了什么、为什么丢"。

剔除粒度按引用的作用分：

| 失败位置 | 处置 |
|---|---|
| `claim`（观点原话） | 整条要点剔除 —— 观点原话是这条要点存在的理由 |
| `qualifier`（限定语） | 只移除限定语字段，并在记录里**明确提示"该要点可能仍带限定，请回看原文"** |
| `support`（印证） | 只移除该条印证，要点保留 |

剔除后若剩余要点少于下限（TBD-B 的 `evidence_point_range` 低值），判定抽取质量不足，中止。

### 3.6 数据流的可验证性

每个中间产物落盘为 JSON（`outputs/_intermediate/`），使得：

- 评审可以只看 evidence 主表就判断抽取质量
- 单步可重跑（改 prompt 后不必重跑全流程）
- §2.7 的自动校验项可以在中间产物上离线跑
- **改动前后可比**（`scripts/snapshot.py`，见下）

**三道检查各盯一层，缺一层就有盲区**：

| 脚本 | 盯的是 | 改 prompt 时会不会红 |
|---|---|---|
| `selftest.py` | 确定性代码层：SRT 解析、原话定位、字数口径 | ❌ 一项都不会 |
| `check.py` | 这一版**合不合规**：引用字面命中、角度 3 个、note_02 被拦 | ❌ 少抽几条照样全绿 |
| `snapshot.py` | 这一版**和上一版差在哪**：要点数、P 编号集合、无出处条数、引用总数 | ✅ 就是干这个的 |

前两道都答不了"我把抽取上限从 16 改成 10，输出到底变成了什么样"。
第三道只报事实（`evidence.要点数 16 → 9`、`要点编号 -P12 -P16`），**不判好坏** ——
和全流程的分工原则一致：程序报事实，判断留给人。

⚠️ 它**只比结构性计数，不比措辞**。`temperature=0.3`，什么都不改原样重跑措辞也会飘；
措辞变了是正常的，编号集合少了四个才是信号。基准存在 `store/output_snapshot.json`，
受众是改 prompt 的人不是编辑，所以不进 `outputs/`。

### 3.9 模型实测结论（原 TBD-G）

实测环境：`deepseek-v4-flash`，走 OpenAI 兼容协议（`https://api.deepseek.com`）。

| 项 | 实测结果 |
|---|---|
| 上下文窗口 | 逐字稿全文（12,677 字）+ 抽取指令 = 19,744 字 prompt，一次进无问题 |
| JSON 结构化输出 | `response_format={"type":"json_object"}` 支持，输出可直接解析 |
| **该模型是推理模型** | `max_tokens` **包含思考链**。入库单次调用实测 out=23,376，其中 **reasoning=22,501** |
| 中文 token 比 | prompt 7,556 tokens ≈ 12,600 中文字符，约 **1 token ≈ 1.7 字** |
| Prompt 缓存 | 命中率高（7,424 / 7,556），同一段 system prompt 重复调用成本显著下降 |
| 单次调用耗时 | 入库阶段约 155s；主要花在思考链上 |

**踩到的坑（已修）**：`MAX_TOKENS=8000` 时，思考链吃满整个输出预算，
`finish_reason=length` 且 `content` 返回**空字符串**。表面症状是"JSON 解析失败"，
根因是配置不足 —— 两者必须区分：

- 前者重试无用，只会重复烧钱 → 代码识别 `finish_reason=length` 后**直接抛错并给出修复指引**
- 后者才值得重试

对应实现：`pipeline/llm.py` 的 `TruncatedError`。

**衍生的 prompt 优化**：思考链日志显示模型在反复自查"这句引用是不是一字不差"。
这件事程序已经做了（`locate_quote` / `find_offset`），于是在 prompt 里明确写出
"校验由程序做，你直接复制原文即可"，把它的算力从自我核对挪回内容判断。

**给业务方的结论**：本方案不绑定推理模型。若追求速度与成本，
换非推理模型（如 `deepseek-chat`）只需改 `.env`，代码零改动。

### 3.10 draft 字数：已由出题方放宽为「合理即可」

> **这是本文档中唯一一处偏离【题目写死】数值的地方，且是出题方本人当面确认的**，不是我方自行放宽——记录在此以便追溯。

**题目原文**：「一篇 500–800 字、可供编辑继续修改的内容初稿 v0.5」。

**出题方口头答复**：**合理即可。**

**现口径**：程序不做区间判定、不输出偏离量、不因字数重写。只保留一个"是不是根本没写完"的地板：

| | 取值 | 作用 |
|---|---|---|
| 语感参照 | 500–800 | 只写进 prompt 当参照，不做任何校验 |
| 地板 | 300 字【MVP 默认值，拍的】 | 低于它说明模型中途截断或返回了残稿 —— 那是**故障**，不是风格问题 |

**为什么不再设上限**：编辑要的是能往上加的初稿，长一点不构成缺陷。真正要防的"写满"（过渡句、铺垫、正确废话）不是长度问题，是**形态**问题，用字数卡不住也不该用字数卡 —— 一篇 500 字的正确废话照样过关。所以这个约束移到了 §2.5 的形态要求和 prompt 的四条禁令里。

**放弃了什么**：旧口径会在交付物里标出偏离量（"624 字，偏离目标区间 -176"）。既然出题方已确认合理即可，这个记账就没有对象了，留着只是让编辑读一行无意义的数字。

**本次运行**：正文 1,630 字。

> ⚠️ 字数口径本身仍写死在 `pipeline/textutil.py:count_draft_chars`（剔除内联证据标记与 Markdown 语法后的非空白字符数）。口径不写死，"多少字"这句话就无法被复现地检验。
> 【实测教训】标记格式从 `[字幕38 …]` 改成 `[P08 字幕38 …]` 时，剔除用的正则没跟着改，导致标记文本被算进正文，1,630 字虚报成 1,972 字。已补进 `selftest.py` 回归。

### ~~TBD-A~~：3 个角度怎么排序 → **已结案**

> ⚠️ 本条原编号为 TBD-B，与 `config.py` 里 TBD-B（要点数量）撞号，已改为 TBD-A。

**来源**：只喂 `evidence.md`，不喂原文（§2.2 Stage 4）。

**排序**：交给 LLM，**但不输出分数**——直接给排好序的 3 个 ＋ 各自理由。

理由：3 个角度全部交付给编辑，最终选择权在人，排序错了代价很低，不值得为它设计规则或评分机制。而分数有两个坏处——LLM 对创意做绝对打分校准很差（Si, Yang & Hashimoto 2024 实测：直接打分 50.0–51.7%，低于人类评审一致性 56.1%），且存在 verbosity bias；更实际的是，**一旦给了分数，编辑就只看分数，理由白写了**。

> 原顾虑"模型生成角度再让模型打分＝循环自评"成立。解法不是换排序机制，是**不打分**。

**硬约束（不变）**：

- 自带"我还没有看到明确证据"的说法（字幕 6）不能做标题
- 戏谑反讽（字幕 4「应该有人花钱让我们闲着」）不能当立场——本条已被 §2.2 的片头排除规则覆盖
- 被限定语约束的主张（字幕 38 的数据）不能做定论式标题

### TBD-B：evidence 该抽多少条要点 → **仍未决**

**占位值 `(8, 16)`**（`config.py:evidence_point_range`），写进抽取 prompt 当宽区间，让模型自己收敛。本次实跑落在 **16 条**。

**为什么不定死**：这个数字的正确取值取决于**编辑一次改稿实际用得上几条**，而这是使用数据，不是能靠再跑一次实验得出的结论。

**但两个方向的失败模式已经知道**：

| 太少 | 太多 |
|---|---|
| 抽漏的东西下游再也找不回来 —— Stage 4/5 只吃 evidence，主表没有的角度阶段无从生成（§2.2 Stage 4 推论） | 退化成"缩写版全文"，等于没做取舍，R1 的「有取舍」判据直接不通过（§2.7） |

**所以下限比上限重要**：漏抽是不可逆的，多抽只是让编辑多划两眼。当前区间偏宽正是这个考虑。

⚠️ 与 TBD-E（关键段上限 10）的区别：那边已经用实验证明"不设上限会退化"，只剩数值待校准；这边**连区间形态本身都还没有依据**。

### ~~TBD-C~~：待核事实怎么判定 → **已结案**

**不加规则捞取层。** 原想法是"正则先捞含数字/比例/年份/机构的句子，模型再判有没有出处"，撤销。

**规则捞的是"长得像事实的句子"，该核的是"没出处的断言"，两者不重合。** 字幕 45「不适应的学校 10 年后将不复存在」没数字、没机构、没比例，正则捞不到，但它是全篇最该核的一条。

而 `evidence.md` 的**印证栏为空**已经是这个信号（§3.4）。所以 `editorial_checks.md` 是主表的视图，不新增调用。

**三类分工**：

| 分类 | 收什么 | 来源 |
|---|---|---|
| 事实 | 无出处的数据 / 机构 / 案例 / 岗位影响 | 规则：类型=事实 ∧ 印证栏空 |
| 风险 | 说话人存疑、口播特征、脱敏遗漏、同源拦截 | LLM 判 ＋ 代码算（同源） |
| **缺失信息** | 缺画面无法消歧的指代、术语不统一、片头与正片对应 | 规则 ＋ LLM |

⚠️ 两个边界：

1. **印证栏为空只对"事实"类有效。观点没有出处是常态，不构成风险信号**——"争议观点"必须由 LLM 从 evidence 判断"写进文章会不会被读者或当事人挑战"，不能用印证栏推。
2. 第三类**沿用题目原词「缺失信息」**。曾一度改叫「存疑信息」，因为当时还收转录疑误（既不是缺失也不是风险，无处安放）；转录层噪音移出该文件后（§3.4），扩名失去理由，已改回。

### ~~TBD-D~~：适用读者匹配怎么判 → **已结案**

**判，但不用它排除。**

必须判——PDF 只在字段说明里提了一句，但另两处是硬要求：README「如存在…**适用读者不匹配**或引用范围不清，请在输出中明确标注需要编辑人工确认」；`content_brief.md`「如历史素材存在日期久远、**适用读者不一致**…应明确说明不复用或仅有限复用」。

**怎么判**：把 brief 的目标读者原文与该篇 `适用读者` 原文一起给模型，只答"有没有交集"。不定标签体系、不打分、不新增调用——挂在 Stage 3 那次匹配调用的输出里加一个字段。

```
适用读者：AI行业从业者、创业者、投资人、科技公司管理者…
→ 一致（交集：创业者、管理者）
```

**为什么可以容忍模型判错**【实测】：8 篇的 `适用读者` 与本次 brief 读者 **7/8 命中**（都是长串罗列，普遍含创业者/管理者/职场人）。唯一不命中的 note_02 已被同源检测拦截。**该字段在本数据集上零信息增益**，判定结果只写给编辑看，不触发任何自动排除，判错无害。

> 原卡点"要编码得先定义标签体系"消解——**不需要排除，就不需要可靠的排除机制**。真正有约束力的是 `可引用范围`（§2.6），那是动作指令，原文抄出来即可。

### TBD-E：关键段抽取的上限 → **仍未决，且有新实测**

**比例上限（10%）作废**，两条独立理由都成立：

1. 历史笔记正文合计 372,942 字【实测】，10% 即约 37,000 字段表，而段表容量估算是 8 篇 ≈ 8,000 字，**差 4 倍以上**，撑不住单篇 82,978 字那种长文
2. 段表存的是**观点句**不是原文片段（§2.2 Stage 0a），跟原文字数不是一个单位

**绝对上限该不该留 → 已用实验定案：必须留。**

2026-08-01 讨论中曾据"一篇本来也提炼不出那么多观点，抽取会自然收敛"主张**取消一切上限**。首次实跑数据已可疑（8/8 篇全部顶格 11–12 段，最短的 12,709 字与最长的 82,978 字抽出一样多，说明决定段数的是上限本身而非素材信息量），随后放开上限重跑验证：

| | 结果 |
|---|---|
| note_01 放开上限 | **抽出 34 段，占正文 15.1%** |
| 段表质量 | 出现**重复 topic_tag**，以及非商业判断的碎片 |

**结论：不设上限时模型会把段表写成缩写版全文**，正是段表要避免的形态。上限保留。

**字数上限取消**：它是段数的从属量，两个上限在重复约束同一件事，留一个即可。

**段数取 10**：现表每篇 11–12 段中真正站得住的约 8–9 条，12 是在放水。
⚠️ 该数值仍**无业务校准依据**，属 MVP 占位（见 `pipeline/config.py` 的 `TBD_PLACEHOLDERS`）。

**同时在 prompt 侧加了两条硬约束**（数量上限治标，这两条治本）：

1. **同一篇内 `topic_tag` 不得重复** —— 重复标签说明模型在把一个观点拆成几条，对匹配没有任何帮助
2. **每条 `claim` 必须独立成立** —— 脱离原文单独读也是一个完整判断。
   反例「具体性是筛选知识的标准」「判断结果的能力对所有人是公平的」：离开上下文没有意义，匹配时也命中不了任何东西

**仍未定的**：10 这个数字本身。它需要的是业务校准（编辑实际用得上几条），不是再跑一次实验。
