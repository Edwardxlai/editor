# AI 增强内容复盘工具

笔记侠 FDE 加速营 · 第二轮实战题目一 · 最小可运行原型

输入一场访谈的逐字稿 + 历史笔记库，输出一套**证据锚定的编辑工作包**：
6 份 Markdown，每一条判断都能回指到具体的字幕序号、时间戳和说话人；
每一条无出处的事实性说法都已被标出；每一条历史素材的复用与否都附判断理由。

## 一、运行环境

**先跑这一条，它会告诉你在你这台机器上现在能跑到哪一步：**

```bash
python scripts/env_check.py          # macOS/Linux 通常要写 python3
```

它只用标准库，在装依赖之前就能跑。检查解释器版本、平台、依赖、输入文件编码、
写权限、`.env` 是否可解析，最后给一句结论。加 `--net` 会额外对 API 端点做一次
TLS 握手（不发请求、不计费）。

| 项 | 要求 |
|---|---|
| Python | 3.9 起可用（低于此版本启动即报错）；**实测版本 3.10.11**，3.9 未逐项验证 |
| 依赖 | 只有 `httpx`、`python-docx` 两个 |
| 系统 | 无平台相关代码：路径全走 `pathlib`，读写一律显式 UTF-8，无 shell 调用 |

**验收不需要装依赖，也不需要 API key。** 下面三条命令在一台只有 Python 的裸机器上直接可跑：

```
python scripts/selftest.py     确定性层自检 27 项
python check.py                验收清单 12 项（读现成的 outputs/）
python run.py --dry-run        导出 prompt 供审查
```

要**重新生成** `outputs/`（即真的调模型）才需要装依赖并配 key：

```bash
# macOS / Linux
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

# Windows PowerShell
py -m venv .venv; .\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

> Homebrew / Debian 的系统 Python 会拒绝直接 `pip install`
>（`error: externally-managed-environment`）—— 建 venv 是绕开它最省事的方式。
> `python-docx` 缺失不阻塞：`pipeline/docx_read.py` 有 zipfile 兜底，实测 27 项自检全绿。

## 二、配置

```bash

```

填入 key。变量名用 `OPENAI_` / `ANTHROPIC_` 而不是厂商专名 —— 任何兼容这两种协议的服务都能直接跑。

```ini
PROVIDER=openai
OPENAI_BASE_URL=https://api.deepseek.com
OPENAI_API_KEY=sk-...
OPENAI_MODEL=deepseek-v4-flash
```

> ⚠️ `.env` 含真实 key，已列入 `.gitignore`。但**打包 zip 时 `.gitignore` 不生效** —— 交付前确认包里只有 `.env.example`。

## 三、启动方式

```bash
python scripts/env_check.py          # 换机器后第一条：环境体检，零依赖
python scripts/selftest.py           # 确定性层自检，不调模型，不需要 key
python scripts/build_style_card.py   # 一次性：解析已发布样稿 → 结构画像
python ingest.py                     # 一次性：历史笔记入库 → 关键段表
python run.py                        # 主流程：产出 6 个交付文件
python check.py                      # 验收清单
```

**先跑 `selftest.py`**：它在不消耗任何 token 的前提下验证整条链路的地基 ——
SRT 解析、原话定位、自动修正、字数口径、同源覆盖率、docx 兜底，共 27 项。
这一层必须是确定性的，所以它必须能被离线验证。

前两步是**离线一次性**的：样稿和历史笔记都是静态的，抽一次永久复用，
不必每次跑主流程时重读（既省 token，也避免风格约束在不同运行间漂移）。

常用参数：

| 命令 | 作用 |
|---|---|
| `python run.py --dry-run` | 只导出 prompt 不调模型，**不需要 API key**。用于审查 prompt |
| `python run.py --cache` | 复用已有中间产物，只跑缺的阶段。改完 prompt 单步重跑用 |
| `python run.py --until extract` | 跑到指定阶段为止（`extract`/`reuse`/`angles`/`outline`/`draft`） |
| `python run.py --angle 2` | 用第 2 个角度写初稿（默认第 1 个） |
| `python ingest.py --only note_03` | 只入库指定笔记（增量合并，不覆盖其他篇） |
| `python scripts/snapshot.py --save` | 把当前输出存为基准（改 prompt 之前跑） |
| `python scripts/snapshot.py` | 与基准比对，打印结构性差异（改完重跑之后跑） |

### 为什么还需要 `snapshot.py`

`selftest.py` 和 `check.py` 都盯不住 LLM 那一层：前者验确定性代码，改 prompt 一项都不会红；
后者验「这一版合不合规」，它不问"要点是不是从 16 条掉到了 7 条"。

也就是说，把抽取 prompt 的「8–16 条」改成「6–10 条」，两道检查全绿，
而 `P16` 可能已经消失、outline 少一节、初稿塌一段 —— 没有东西会提醒你。

`snapshot.py` 就补这一格：跑完打印 `evidence.要点数 16 → 9`、`要点编号 -P12 -P16` 这类事实。
**只比结构性计数不比措辞**（`temperature=0.3`，原样重跑措辞本来就会飘），
**只报变化不判好坏** —— 接不接受由人定。它是给改 prompt 的人用的，不进 `outputs/`。

### ⚠️ 用推理模型时必须调高 `MAX_TOKENS`

DeepSeek-V4 系列、o 系列等推理模型的 `max_tokens` **包含思考链**。
实测 `deepseek-v4-flash` 单次入库调用消耗 23,376 输出 token，其中 **22,501 是思考**。
设成 8000 会让思考链吃光预算，正文返回空字符串。

代码会识别这种情况（`finish_reason=length` 且正文为空）并直接报错给出修复指引 ——
**不会重试**，因为这是配置问题，重试只是重复烧钱。

推荐 `MAX_TOKENS=32000`；换非推理模型（如 `deepseek-chat`）可显著提速降本，只需改 `.env`。

## 五、输出位置

```
outputs/
├── angles.md              3 个内容标题 / 切入角度备选
├── outline.md             文章结构与关键要点（两级标题树）
├── evidence.md            关键观点对应的原始素材证据 ★ 主表
├── reuse_suggestions.md   历史内容复用建议 / 为什么不应复用
├── draft_v0_5.md          可编辑初稿，含内联证据标记
├── editorial_checks.md    需编辑人工确认的事实、风险与缺失信息
└── _intermediate/         各阶段中间产物 JSON（可单步重跑、可离线校验）

store/
├── segments.jsonl         关键段表（ingest.py 产出）
├── notes_meta.jsonl       历史笔记篇级元数据
├── style_card.md          风格卡（人定稿，结论已写进 prompts/，运行时不再读取）
└── style_samples_raw.md   样稿结构画像（机器提取）
```

**★ `evidence.md` 是主表，其余五个文件都是它的视图。** 抽取只跑一次，
下游只做筛选与引用，不重新抽取。这样证据溯源天然成立：角度引 `P` 编号，
`P` 编号本来就挂着说话人和时间戳。

六个文件是编辑动线上的一条链，**每份只做自己那一环，不预演下一环**：

```
angles 选  →  outline 搭  →  evidence 查  →  draft 写  →  reuse 补  →  checks 核
```

所以 outline 里不摆原话（那是 evidence 的活），angles 里不写选题方法论
（那是 PRD 的活），checks 里不列时间戳重叠（编辑不会因此改任何一个字）。
**`outputs/` 只放编辑当天要用的东西。**

## 六、这个原型的关键设计

### 1. 能用代码算出来的事实，不问模型

模型只负责一件它不可替代的事：**从原文里挑出哪句话值得引**。

说话人是谁、时间戳是多少、这句话在第几条字幕，**全部由代码从逐字稿反查得出**
（`pipeline/validate.py`）。结果是：溯源信息正确不是靠模型自觉，而是结构上不可能错；
模型唯一可能出的错 —— 引了原文里不存在的话 —— 会被 `locate_quote` 当场抓住并中止。

### 2. 空的支撑栏必须显式写"无"，但空栏对两类要点意味着不同的事

一条要点如果全篇找不到支撑，`evidence.md` 里会显式渲染成 `| — | **无** | — | — | — |`。
**空栏本身就是给编辑的信号。** 但它意味着什么，取决于这条是事实还是观点：

| 类型 | 这一栏问的是 | 空着意味着 |
|---|---|---|
| `事实`（含数字、研究、机构） | 他拿什么**证据**支持这个数字 | 🔴 无出处，写进正文前必须核 |
| `观点` / `案例` / `因果链` | 他**为什么这么认为**（理由、因果） | 正常，他直接下了判断没展开 |

早期版本对两者一律打「纯断言」警告，是范畴错误：它让「教育成本降到 100 美元」
和「企业家就是能动性的同义词」长得一模一样。**区分这两件事恰恰是这个工具最该做的。**

### 3. 生成角度时只喂要点表，不喂逐字稿原文

把整篇原文丢给模型让它"提炼角度"，等于让它自己找重点 ——
它做不到取舍，只能取平均，输出全篇的最大公约数，也就是那句正确的废话。
**平庸是这个操作本身决定的，不是提示词写得不好。**

### 4. 初稿是一篇能读的文章，不是提纲的展开

题目原文写「500–800 字」，**已向出题方确认「合理即可」**，因此代码不做区间判定，
只保留一个"是不是根本没写完"的地板（300 字）。

真正的约束不在长度，在形态。最容易犯的错是把 outline 每节改写成一段话、
四段并排交差 —— 那不是初稿，那是把结构文件抄了一遍，编辑已经有一份了。

| ❌ 提纲的展开 | ✅ 初稿 |
|---|---|
| 每节一段，段与段之间没有关系 | 上一段的结尾把下一段的问题带出来 |
| 每段都从"嘉宾X说"开头 | 先立判断，原话用来钉住它 |
| 写完最后一个要点就结束 | 落在一个判断上，留给编辑续写的接口 |

放开长度不等于可以写满：多写的每一句仍然得是判断或证据。
AI 给 8000 字大多是过渡句和正确废话，编辑要**删**；而删比加累。

**本次实测的取舍**：抽出 16 条要点，进结构 12 条，`outline.md` 末行交代了没进的 4 条
（`P09`、`P10`、`P11`、`P13`）。这四条恰好就是全部四条**无出处的事实类要点** ——
终生收入下降超五分之一、教育成本约 100 美元、用 AI 学习省 60% 时间、学校 10 年后不复存在。
它们全部躺在 `editorial_checks.md` 的待核清单里，等编辑核完再决定要不要写进去。

⚠️ 但这是**这次运行的结果，不是机制保证**：prompt 里没写"无出处不得进结构"，代码也没校验它。
写成机制就是夸大，所以只作为实测记录说明（PRD §2.2 Stage 5 同注）。

### 5. 同源笔记由代码算，不问模型

历史笔记里可能混着**本次访谈的另一个整理版本**。引用它等于拿素材佐证素材，
还会制造"历史上已有观点支持"的错觉。

这件事在发 prompt 之前就用字符 8-gram 覆盖率算完了 ——
【实测】note_02 覆盖率 0.8913，其余 7 篇 ≤ 0.0001，差三个数量级，
任何阈值都分得开。让模型读两份长文本自己"感觉像不像同一场"既贵又不稳定。

两处去重的位置不同，问的也是两个问题：

- `ingest.py`：**库内互重** —— 同一篇内容的两个整理版本不能同时进库。
- `run.py` reuse 阶段：**与本次输入同源** —— 不删库（换一场访谈它就恢复可用），
  只在发 prompt 前过滤掉。

### 6. 宁可报错，不可伪造

任何一步失败都显式抛出并中止，不产出兜底内容。半成品比报错更危险 ——
它看起来能用。

## 七、不用 RAG / Agent 的理由

检索是为了"从大量内容里找出相关的少量"。这里两侧都不大：
逐字稿 12,677 字，关键段表 8 篇约 8k 字，都能一次读完。
上向量库只会引入召回损失和额外依赖，换不来任何东西。

段表能撑到百篇量级；超过之后再分表或上检索层 —— 那是规模问题，不是这一版的问题。
完整论证见 [PRD §2.3](PRD.md)。

## 九、跨平台验证

不知道拿到这个包的机器是什么，所以把"换一台机器会坏在哪"当成一类故障来测。
下面每一行都是实际跑出来的结果，不是推断（复现方式见 `scripts/env_check.py`）：

| 验证项 | 结果 |
|---|---|
| 平台相关代码 | **零**。全仓库无 `os.name` / `sys.platform` / `subprocess` / shell 调用 / 硬编码盘符 |
| 工作目录 | 路径全部由 `__file__` 推出，从任意 cwd 用绝对路径调用均正常 |
| 语法版本下限 | 按 3.8 语法编译全部 14 个 `.py`，0 处不兼容；运行时下限设在 3.9 并在 `config.py` 顶部显式挡一道 |
| **零依赖可跑** | 屏蔽 `httpx` + `python-docx` 后：`selftest` 27/27 绿、`check` 12/12 绿、`run.py --dry-run` 正常导出 —— 样稿解析自动降级到 zipfile 兜底 |
| `.env` 带 BOM | 修复前首行的键会变成 `﻿OPENAI_API_KEY`，报"缺少 API key" 且肉眼看不出；现按 `utf-8-sig` 读，实测带 BOM 仍正确取到 key |
| CRLF / LF | 输入文件现为 CRLF，SRT 解析按 `\r?\n` 切块，其余走 Python 通用换行；两种行尾等价 |
| 控制台编码 | 各入口第一件事调 `config.setup_stdout()` 切 UTF-8；`env_check.py` 另有 ASCII 降级路径，终端编码不足时用 `[ OK ]` 代替 `✅` |
| 中文路径 | 项目目录名含中文，但**代码引用的路径全是 ASCII** —— 压缩包在 macOS 解压若文件名乱码，只影响文档链接，不影响运行 |

**修掉的两个真 bug：**

1. `run.py --dry-run` 被 README 写成"不需要 API key"，但 `run.py` 顶层 import 链会拉进 `httpx` ——
   在没跑过 `pip install` 的机器上连 `--dry-run` 都起不来，报的还是 ImportError。
   现改为延迟导入（`pipeline/llm.py:_httpx`），承诺才真正成立。
2. `.env` 的 BOM 问题（见上表）。这类故障最难自查：配置看起来完全正确。

**仍未覆盖：** 只在 Windows / Python 3.10.11 上实机跑过完整流程。
Linux、macOS 与 3.9 是**静态与模拟验证**（语法编译、依赖屏蔽、编码注入），不是真机实测。
`env_check.py` 的作用正是把这段差距挪到对方机器上当场暴露，而不是等它在半路炸开。

## 十、已知限制

| 限制 | 说明 |
|---|---|
| 未定阈值 | **两项**未定案：evidence 要点数量（占位 `8–16`）、单篇关键段上限（占位 `10`）。都写在 `pipeline/config.py:TBD_PLACEHOLDERS`，论证见 PRD §4-B / §4-E。它们要的是业务校准（编辑实际用得上几条），不是再跑一次实验<br>（角度排序、待核事实判定、读者匹配三项曾经未决，均已结案，结论见 PRD §4） |
| 不做事实核实 | 无联网、无权威源。工具只标出"什么需要核实"，核实由编辑做 |
| 不做读者匹配自动判定 | `适用读者` 是自然语言，编码需先定义标签体系，目前无依据。原文列出该字段 + 标"需编辑确认" |
| 单篇处理 | 未做多篇批处理 |
| 无原始视频 | 部分指代（如"你的例子是护士录笔记"）无法消歧，已列入 `editorial_checks.md` |
